# mem-ontology/

`lehrplan-th-shadow.ttl` is a Mem-schule (FWU MEM Lehrplan ontology,
[mem.schule](https://mem.schule/)) -shaped Turtle export of EvoMentor_DE's
full Thuringia Grades 5-10 Lernziel dataset (`data/lernziele_MNT56.json`,
`data/lernziele_gy78.json`, `data/lernziele_gy910.json`), generated by
[`scripts/export_mem_th_shadow.py`](../scripts/export_mem_th_shadow.py).
Regenerate it any time the source data changes:

```
python scripts/export_mem_th_shadow.py
```

## Why "shadow graph," not a real MEM contribution

FWU's live SPARQL endpoint (`https://sparql.mem.edufeed.org/sparql/`) has
curriculum data loaded for exactly four states — Bayern, Brandenburg,
Sachsen, Rheinland-Pfalz — confirmed live 2026-08-22 by querying the
endpoint directly (`memschule graphs`, or see the sibling `mem-schule`
toolkit's `docs/graphs.md`). **Thuringia has no curriculum data loaded
upstream.** There is nothing real to crosswalk EvoMentor_DE's data against
yet, so this file reuses every real, live-verified shared FWU individual/
predicate/class it can, and mints new individuals only for the
Thuringia-specific curriculum content that doesn't exist anywhere upstream —
following the exact same "modular per-state subclass" convention FWU's own
ontology already uses for BY/BB/SN/RP (e.g. `LehrplanPLUS (BY)` as a
subclass of the core `Lehrplan` class; this file defines `Fachlehrplan_TH`,
`Lernbereich_TH`, `Kompetenzerwartung_TH` the same way).

All locally-minted individuals live under a clearly provisional namespace,
`https://openevo-ccs.github.io/EvoMentor_DE/lehrplan-th-shadow/` — never
under `w3id.org/lehrplan/th`, which is FWU's own namespace, reserved for if
and when they (or a partner) publish real Thuringia curriculum data.

## What's real/live-verified vs. locally minted

Queried directly against the live endpoint on 2026-08-22 (not assumed from
documentation — the same discipline the `mem-schule` toolkit's own docs
insist on):

| Individual | URI | Verified via |
|---|---|---|
| Bundesland Thüringen | `lp:LP_3000031` | `?s a lp:LP_0000040 ; rdfs:label ?l` filtered to `"Thüringen"@de` |
| Schulart Gymnasium (TH) | `schulart:TH_0000006` | same pattern against `schulart/TH_*` |
| Schulfach Biologie (TH) | `schulfach:TH_0000002` | same pattern, label `"Biologie"@de` |
| Schulfach Mensch-Natur-Technik (TH) | `schulfach:TH_0000028` | same pattern, label `"Mensch-Natur-Technik"@de` |
| Jahrgangsstufe 1 / 7 | `lp:LP_2000001` / `lp:LP_2000007` | direct `rdfs:label` lookup; confirms the `LP_200000N` pattern schema.md documents, so grades 5–10 = `LP_2000005`…`LP_2000010` |

Predicates reused as-is (all real, core FWU ontology, in the
`https://w3id.org/lehrplan/ontology/` namespace unless noted):
`lp:LP_0000537` (hat Schulfach), `lp:LP_0000812` (für Schulart),
`lp:LP_0000026` (hat Jahrgangsstufe), `lp:LP_0000029` (von Bundesland),
`obo:BFO_0000051` (has-part, `http://purl.obolibrary.org/obo/`).

Deliberately **not** reused: FWU's `hat Titel` predicate links to a "Titel
annotation object" whose exact shape wasn't independently verified this
session — `rdfs:label` is used instead for every human-readable title
(unambiguous, universally valid, doesn't require guessing an unverified
structure).

## has-part transitivity

Matches the real graphs' documented behavior (`mem-schule`'s
`docs/schema.md`) exactly: each `Fachlehrplan_TH` individual has-parts
**every** descendant directly — both its `Lernbereich_TH` children and every
leaf `Kompetenzerwartung_TH`, flattened, not just one hierarchy level. This
was verified after generation (see the script's own validation step, plus a
manual rdflib check): the Gy 7–8 `Fachlehrplan_TH` has 93 direct `has-part`
targets — 3 Lernbereiche + all 90 Lernziele. Any tool written against real
MEM graphs that groups children by `typeLabel`/`rdf:type` instead of
graph depth (the way `memschule tree()` already does) will handle this file
correctly without modification.

## What's intentionally out of scope

**KMK Basiskonzepte Biologie is not modeled as MEM/LP_ classes.** It's a
separate, national, cross-cutting framework with no representation in FWU's
Lehrplan ontology (confirmed by EvoMentor's own
`canonical-curriculum-item.schema.json` `frameworkTags` field comment — this
was independently re-confirmed, not assumed, when this file was designed).
Each `Kompetenzerwartung_TH` instead carries plain string-literal properties
(`evomentor:basiskonzeptPrimaer` / `evomentor:basiskonzeptSekundaer`)
pointing at the exact same `"kmk-basiskonzepte-biologie:bk_..."` tag ids used
by `conceptbase`'s RFC-0018
(`framework-relations/KMK-BASISKONZEPTE-BIOLOGIE-RELATIONS-v1.0.0.yaml`) —
deliberately cross-referenceable across both artifacts, not duplicated
modeling of the same framework in two incompatible shapes.

## Relationship to EvoMentor (v2)

EvoMentor's `canonical-curriculum-item.schema.json` already declares
`"fwu-lehrplan-ontologie"` as a first-class `sourceFormat`
(`individualUri` + `landOntology` + `coreOntologyVersion`) — real input for
that importer path is exactly what this file is. Today, EvoMentor_DE's
Thuringia data only reaches EvoMentor v2 through the generic `"custom"`
`sourceFormat` (`importers/thuringia_custom_importer.py`), and only for the
90 evolution-annotated Gy 7–8 items — a fraction of the 271 Lernziele across
Grades 5–10 this file covers. A `fwu-lehrplan-ontologie` importer reading
`individualUri`s from this file (`landOntology: "lehrplan-th-shadow"`)
instead of `thuringia_custom_importer.py`'s ad hoc join would close that gap
for the full grade range, not just the evolution-annotated subset — left as
a follow-up, not built here.

## Basiskonzept-Kohärenzfäden layer

If `data/kohaerenzfaeden.json` exists, the exporter also emits a small,
explicitly non-FWU annotation layer: each `evomentor:kohaerenzfaden`
(coherence-thread) individual links back to every `Kompetenzerwartung_TH`
that is one of its real stations, via `evomentor:teilVonKohaerenzfaden`. This
is deliberately a *different, weaker* predicate than
`obo:BFO_0000051`/`evomentor:buildsOn` above — coherence-thread membership is
a proposed pedagogical connection this project is recommending, not an
asserted curricular prerequisite, and the two must never be conflated. See
[`docs/basiskonzepte-kohaerenz-strategie.md`](../docs/basiskonzepte-kohaerenz-strategie.md)
for the full method and the worked threads themselves.

## Loading it

Any RDF tool works — it's plain, valid Turtle (validated at generation time
via `rdflib.Graph().parse(..., format="turtle")`):

```python
import rdflib
g = rdflib.Graph()
g.parse("mem-ontology/lehrplan-th-shadow.ttl", format="turtle")
```

To actually exercise `mem-schule`'s own `traversal.py`/`queries.py` against
it (rather than the live SPARQL endpoint), load it into any local triple
store (Jena Fuseki, Oxigraph, a local Virtuoso) as a named graph and point
`memschule`'s `.env` endpoint override at it — not attempted in this
session, since it requires standing up local triplestore infrastructure
outside this repo's scope.
